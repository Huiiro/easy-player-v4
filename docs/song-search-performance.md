# 歌曲搜索性能与后台状态

日期：2026-10-16。原始数据：[2500/10000 首优化前](./song-search-performance.json)、[20000 首优化前后对比](./song-search-performance-20k.json)。

复现当前实现：`npm run perf:song-search -- --sizes=20000 --output=docs/song-search-performance-20k.json`。可通过 `--baseline=旧版searchQuery.ts的路径` 额外比较旧查询；本次对比在修改前保存了旧源码，使用相同数据库逐项验证命中数、ID 顺序和搜索分数一致。

## 测试条件

- Intel Core i7-14700KF，Electron 39.8.10 / Node 22.22.1。
- 项目目录下创建独立的临时磁盘 SQLite 数据库，使用 WAL。没有读取或修改用户曲库和媒体文件。
- 40% 中文、40% 日文、20% 英文；歌曲标题带唯一编号，歌手/专辑重复共享。不是用户真实曲库，不代表所有大曲库分布。
- 使用实际搜索词条生成器、Worker、后台索引服务、数据库触发器和 repository 查询。没有将同一份预生成词条复制到整库来代替真实转换。
- 旧报告先构建 2500 首并测查询，再追加 7500 首构建到 10000 首。新报告独立构建 20000 首。
- 查询在索引完成后执行，数据库缓存较热；每项执行 7 次，下表取中位数。包括查询、相关度排序、总数计算、对象映射和 JSON 序列化，不包括 Electron IPC 传输、Vue 更新、虚拟列表和封面加载。

## 20000 首查询优化

原来的 SQL 每次查询逐行调用 JavaScript 规范化原始字段，再反复判断命中、计算相关度。本次调整为：

- 数据库 v7 增加 `song_original_fts`，原文字段在迁移或变更时完成 NFKC/小写规范化，使用 FTS5 trigram 索引。至少三个 Unicode 字符的原文先用索引缩小候选集，再用 `instr` 核验；一、二字符和含 NUL 的输入使用原生 SQLite `instr`，保留任意位置包含匹配。
- 读音继续使用已有 FTS5 索引。按关键词生成命中 ID 和分数，每词取所有字段/匹配方式的最高分，多词取交集并累加；权重、范围过滤、排序和分页语义保持一致。
- 命中 ID/分数暂存到连接内的 TEMP 表，同一搜索词用于总数、分页或不同范围时可复用。通过 `total_changes()` 和 `data_version` 检测本连接及其他连接的写入；事务中的查询不复用缓存，避免回滚造成陈旧结果。任何数据库写入均会保守失效，包括后台索引写入。
- 该迁移一次性建立原文索引；已有 v3 读音无需因此重新转换。新增/改名/删除由触发器同步原文索引，读音仍按后台队列更新。

下表为当前页面返回全部命中的方式，包含实际 repository 查询、相关度排序、总数、对象映射和 JSON 序列化的中位数：

| 查询             | 命中数 |  优化前 |  优化后 |
| ---------------- | -----: | ------: | ------: |
| `qili`           |    800 |  60.7ms |   6.0ms |
| `qlx zjl`        |    800 |  71.3ms |  12.1ms |
| `kirei`          |    800 |  61.0ms |   6.3ms |
| `夜`             |   8800 | 126.0ms |  70.0ms |
| `周杰伦`         |   8000 | 149.4ms |  59.9ms |
| 无结果英文词     |      0 |  50.3ms |   0.8ms |
| 空搜索，整库浏览 |  20000 | 115.8ms | 114.3ms |

每项七次，计时前通过不影响搜索字段的写入主动失效缓存，避免把重复查询缓存命中当作新关键词的性能。所有对比样本命中数、ID 顺序和分数一致。优化后的非空查询样本最大值 71.7ms；相同数据仅返回前 50 首时，常见读音约 2.4～8.3ms，`夜`/`周杰伦` 约 16.7/18.1ms。

宽泛查询返回 8000～8800 首，JSON 约 5.6～6.4MiB；整库浏览约 14.4MiB。页面目前仍返回全量结果，清空搜索和宽泛查询的传输、对象构建与渲染仍有成本。夹具没有大段歌词，真实歌词/标签数据可能进一步增加开销。上述数值不包含 200ms 防抖、IPC 和页面渲染，不能据此承诺端到端延迟。

本轮首次后台索引 20000 首约 232.8 秒，其中每批 100 首之间的主动等待约 200 秒。索引期间基准主线程事件循环延迟 p99 49.6ms、最大 138.4ms。数据库约 165.5MiB；基准进程 RSS 约 1028MiB，包含词典 Worker、缓存、优化前后两份运行时与查询对象，不能解释为正式应用的新增内存。

## 旧报告的索引构建

| 阶段                             |     耗时 |
| -------------------------------- | -------: |
| 首批 2500 首，包含词典首次初始化 |  28.6 秒 |
| 追加 7500 首至 10000 首          |  86.2 秒 |
| 两阶段累计                       | 114.7 秒 |

这些耗时包含后台服务每批最多 100 首、批次间等待 1 秒的调度策略，累计约 100 秒来自主动等待。不要将 115 秒解释为纯转换计算耗时，也不要将两阶段累计解释为单次完全冷启动 10000 首的精确测量。常规启动只处理缺失/变更/版本过旧的记录，不会每次全库重建。

索引构建期间基准主线程事件循环延迟：2500 首阶段 p99 20.4ms、最大 112.4ms；追加至 10000 首阶段 p99 36.6ms、最大 79.9ms。这不是完整播放器运行中的音频稳定性测试。

10000 首完成后测试数据库约 80.3MiB，包含基础曲库、派生词条、FTS 和 SQLite 空间开销；本次原始字段较短，但唯一编号会增加词条。基准进程 RSS 约 520MiB，包含该 Node 进程、词典 Worker 和缓存，不能等同于正式应用的新增内存。当前词典 Worker 在索引结束后仍保留，以供增量更新复用。

## 页面上的后台状态

顶栏仅在存在待处理任务且处于排队或构建索引时显示状态入口。完成、空库、纯播放暂停、等待重试或错误时隐藏，并关闭已经展开的面板；后续恢复工作会重新出现。点击可展开：

- 全部读音已经完成的数量、剩余数量、进度条与当前歌曲。
- 当前排队或处理中的状态。
- 待重试数量及下次重试时间。只有基础词条生成成功、日语读音仍待重试的歌曲，不计为完整完成。

状态由主进程提供初始快照与事件推送，处理过程中最多约每 250ms 推送一次，批次/模式变化即时更新；空闲状态不重复推送不变的数据。计数来自实际数据库，新增、删除、改名均会反映。首次快照使用修订序号防止覆盖更新的实时进度，组件卸载时清理监听和重试定时器。

## 当前判断与后续优先级

本次 20000 首混合数据下，常见读音查询已降至约 6～12ms；宽泛查询返回数千首时约 60～70ms。后续若真实页面仍有停顿，应优先测 IPC/页面更新并处理全量结果传输，例如列表摘要或分批加载。更大规模曲库应补充 5 万/10 万首、冷缓存以及真实播放器端到端测试，再判断是否将数据库查询移入读线程。
